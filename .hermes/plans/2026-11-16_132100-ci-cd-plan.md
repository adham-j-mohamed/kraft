# CI/CD-plan för Kraft

Datum: 2026-11-16
Författare: addejj

Syfte
- Införa en robust CI-pipeline som verifierar PR:er och typkontroll, och en CD-pipeline som deployar till aj-lab automatiskt vid push till main enligt projektets driftregler.

Krav och förutsättningar
- Hemligheter hålls utanför repot: APP .env ligger på aj-lab (~/kraft/.env) och får aldrig kopieras in i CI. CI använder en SSH-nyckel (GitHub Secret) för att rsync:a koden till aj-lab och exekvera deploy-steg.
- Endast push till main/deploy-branch triggar produktion.
- En commit per steg och verifiering med siffror. Alla ändringar i hjälpsida eller beteende måste uppdatera /help-texten i samma commit.
- Ingen automatisk ändring av Cloudflare-tunnlar eller Access via CI.

Översikt (högnivå)
1. PR pipeline (push/PR mot branch)
   - Steg: checkout, node-caching, npm ci, npx tsc --noEmit, npm run lint (om finns), enhetstester (finns få idag), build (next build) — för att få tidiga fel.
   - Artefakt: caching inga, men build-artifact kan sparas som artifact för snabbare reproducerbarhet.
   - Godkännande: PR får inte mergas om pipeline misslyckas.

2. Release -> main
   - På push till main: kör samma CI-steg (typkontroll + build) i "release"-jobb.
   - Efter lyckad build: kör deploy-jobb som RSYNC:ar arbetskopian till aj-lab:~/kraft och kör samma sekvens som manual-deploy:
     a) docker compose -f docker-compose.yml up -d db
     b) docker compose -f docker-compose.yml run --rm tools node scripts/migrate.mjs
     c) docker compose -f docker-compose.yml run --rm tools node scripts/seed.mjs
     d) docker compose -f docker-compose.yml up -d --build app
   - Efter deploy: sanity-check mot APP_URL/api/health. Vid fel: markera deploy som failed och skicka notis.

3. Säkerhets- och driftsregler
   - CI använder följande secrets (GitHub Secrets):
     - AJ_LAB_SSH_PRIVATE_KEY (privat nyckel för addejj@aj-lab)
     - AJ_LAB_SSH_USER (ex: addejj)
     - AJ_LAB_HOST (ex: aj-lab)
     - AJ_LAB_APP_DIR (~/kraft)
     - KNOWN_HOSTS (eller använd actions/checkout + setup-ssh- known-hosts)
   - .env och node_modules ignoreras i rsync (samma som scripts/deploy.sh).
   - Ingen secret skrivs ut i jobbloggen.

4. Rollback
   - Manual rollback: revert commit på main + push triggar deploy av föregående release.
   - Alternativ (framtid): behåll senaste image/tag på server och ha ett "rollback"-skript som startar senaste image:docker image:tag.

5. Observability och notifieringar
   - Efter deploy körs healthcheck mot /api/health; vid 200 ok markera deploy som succeeded.
   - Skicka notiser till angiven kanal (t.ex. e‑post eller Slack) vid failure. (Konfigureras senare; kräver webhook-secret.)

6. Staging / förhandsgranskning (valfritt)
   - Om önskat: implementera en staging-branch (staging) eller GitHub environments som deployar automatiskt till en separat katalog eller annan hostname i tunneln. Kräver separat värdregel i Cloudflare. Rekommenderas för stora ändringar.

7. Automatiska tester för offline-flush (framtida jobb)
   - Jobb för e2e offline: köra en headless Chromium (Playwright) som:
     1) installerar appen (serve build lokalt eller via rsync->aj-lab och proxya),
     2) simulerar offline i page.setOffline(true), utför en skrivning (logga set/water/weight), kontrollera att fetch svarar 202 och att en placeholder visas i UI,
     3) återställ online, vänta på SW-postMessage eller kontrollerat resultat och verifiera att server har raden (via API eller DB-read).
   - Detta kräver mer tid att implementera; schema och testkonton måste hanteras noggrant.

8. Praktisk implementation (första leverans, minimal) — steg för steg
   1) Skapa GitHub Actions-workflow .github/workflows/ci.yml som kör PR‑kontroller: tsc, lint, build. (Commit 1)
   2) Skapa .github/workflows/deploy.yml som kör på push till main och:
      - bygger (validator),
      - använder SSH key för rsync till aj-lab (scripts/deploy.sh),
      - kör migrate/seed och docker compose build/up (via ssh remote commands),
      - verifierar /api/health. (Commit 2)
   3) Lägg in instruktion i README.md och AGENTS.md om hur man sätter GitHub Secrets och vem som får deploya. (Commit 3)
   4) (Valfritt) Lägg till en manual promt i deploy.yml för skyddad production deploy (GitHub Environments/required reviewers). (Commit 4)

9. Kontroller innan vi aktiverar
   - Bestäm vilken SSH-nyckel och användare CI ska använda. Skapa en dedikerad nyckel för CI, lägg public key i aj-lab authorized_keys för CI‑användaren.
   - Lägg inte in .env i repot. Verifiera att aj-lab:~/kraft/.env finns och är korrekt.
   - Testa deploy-jobbet från en fork eller test-branch först.

10. Uppföljning
   - När pipeline körs framgångsrikt i två deployer: aktivera notifieringar och schemalagd backup (steg 11 i planen). Dokumentera i AGENTS.md.

Facit-krav vid leverans (vad som måste mätas/raporteras direkt efter aktivering)
- PR-pipeline: lyckas för ett sample-PR (tsc green, build green)
- Push->main: lyckad deploy som slutförs automatiskt och /api/health returnerar {"ok":true,"db":"up"}
- Inga .env-värden syns i CI-loggarna
